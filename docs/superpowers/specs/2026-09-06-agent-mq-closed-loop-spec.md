# Agent RAG 与 MQ 业务闭环升级规格

日期：2026-09-06；目标分支：`agentRag`。

## 边界

仅后端；保留 Spring AI 1.0.0，不引入 MCP，不修改前端，不启动应用、Docker 或外部中间件。本次实现以可验证的预约闭环为核心，不把短信/邮件日志称为真实送达。真实基础设施验收另行由用户授权。

## 现状与问题

已有受控 Agent 工具循环、找房/详情/费用/知识工具、Redis 预约草稿、人工确认事务、Outbox 和 RabbitMQ。但草稿没有结构化 SSE 输出；消费者仅打印短信、转发第二条消息而未可靠确认，通知消费者不落库；Redis 去重将“处理中”当成“完成”；Agent 无法读取真实异步处理结果。发布批次的租约可能在整批发完前到期。历史以换行切分会破坏多行消息；本地知识无匹配时仍返回无关资料。

## 目标链路

用户问题 → Agent 调用只读工具 → `create_appointment_draft` → SSE `appointment_draft` → 用户显式调用确认 API → 同一 MySQL 事务保存预约、确认幂等记录、Outbox → 发布器等待 RabbitMQ confirm 且检查 return → 创建队列消费者事务性保存站内通知 → REST / Agent `get_appointment_status`、`list_my_notifications` 查询真实结果。

MQ 是异步送达的必经路径：确认服务不直接创建通知。Agent 不获得确认预约、发送 MQ 或修改业务状态的工具。通知查询工具只从认证 ToolContext 获取用户身份，不接受模型指定 userId。

## 可靠性设计

1. 保留现有预约事务和 token 幂等。MQ 至少一次投递，MySQL 唯一事件键保证通知业务效果幂等，不宣称端到端 exactly-once。
2. 主创建队列直接消费并持久化通知，消除不可靠的二次转发窗口。旧通知队列保留兼容处理，亦落库；新闭环不依赖它。
3. 消费落库成功后返回由监听容器 ACK；失败有限重试后拒绝进入现有 DLQ。DLQ 不再被日志消费者自动吃掉，保留消息用于人工重放。通知失败不自动取消预约。
4. 以 Outbox attempts 作为租约代数进行完成/失败更新的 fencing；默认每次仅认领一条，避免多条排队发送超过租约。宕机后租约过期可重新认领；重复消息仍由数据库唯一键收敛。
5. 状态区分预约业务状态和消息状态：`PENDING`、`PUBLISHED`、`DELIVERED`、`FAILED`、`UNKNOWN`。DELIVERED 仅表示站内通知已经落库，不表示短信到达。优先以通知记录认定送达，避免确认回调晚于消费的竞态。
6. 查询接口对当前用户过滤，不存在和无权限统一返回不存在；列表有硬上限。读通知操作也校验所有权。
7. 共享组件明确使用 MySQL 数据源，避免误用 pgvector 的 JdbcTemplate。

## Agent / RAG 配套改进

- 模型引擎输出结构化草稿事件（含 token 与过期时间），由客户端显式确认；旧 SSE 类型保持兼容。
- 注册预约状态及站内通知只读工具，工具结果进入可追踪观察记录；没有模型时规则回退也支持预约状态/通知查询。
- 保存结构化 JSON 消息历史，兼容旧缓存；缓存异常不把已成功的工具结果变成重复执行。
- 本地知识无匹配不再补充无关政策，证据不足明确提示。补充与此相关的离线测试。
- 模型回退共用请求时间和步数预算；一旦已请求业务工具，失败后不重新开启工具循环，而保留已经获得的结构化观察（尤其是预约草稿）。线程取消为尽力而为，不能声称撤销了已发生的外部操作。
- 本次不承诺完整长期记忆、任意步骤恢复、多 Agent、自动预约、外部短信网关或未经测量的召回率提升；这些不属于完成闭环的先决条件。

## 数据及接口

新增 V5 迁移：`user_notification`，含唯一 `event_key`、可空 outbox event_id、appointment_id、user_id、type、content、created_at、read_at，按用户时间索引。

- `GET /app/ai/appointments/{appointmentId}/status`：返回当前用户预约及异步投递状态。
- `GET /app/ai/notifications?limit=20`：返回最近站内通知（上限 50）。
- `POST /app/ai/notifications/{id}/read`：幂等标记本用户通知已读。
- 现有创建草稿与确认 API 路径不变。

DLQ 原消息保留，不暴露内部异常或联系人信息给日志/API。失败恢复采用运维核查后重新投递原消息；不得直接重新提交预约。可查失败状态不等于已经具备自动修复。
