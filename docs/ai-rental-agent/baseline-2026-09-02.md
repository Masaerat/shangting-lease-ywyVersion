## 3. 现有业务闭环

当前后端已经具备以下能力：

1. `POST /app/ai/chat` 返回 SSE。
2. `RentalChatServiceImpl` 在模型引擎不可用时切换到 fallback 引擎。
3. `RoomSearchTool` 查询 MySQL 中已发布房源。
4. `LocalRentalKnowledgeService` 从 classpath Markdown 检索租房知识。
5. 预约草稿保存在 Redis，并通过一次性令牌确认。
6. 预约确认写入 `view_appointment`、幂等记录和 Outbox。
7. RabbitMQ 发布失败时由 Outbox 保留待重试事件。
8. 预约列表接口可以查询确认结果。

现有模型路径的主要缺口是：`ModelRentalChatEngine` 先做一次向量检索，再调用一次 `ChatClient`；工具调用、权限、步骤上限和执行轨迹没有形成显式 Agent Runtime。

## 5. PGvector 真实状态

- PostgreSQL `lease_vec` 可连接。
- `vector_store` 已存在。
- 向量总数 13，其中房源向量 12、普通文档向量 1。
- 当前普通文档 metadata 只有 `docId`、`source`、`docType`、`namespace`。
- 当前房源 metadata 只有 `source`、`docType`、`roomRef`、`namespace`，缺少 roomNumber 和 rent。

结论：需要通过代码补充 metadata，并在重建索引时生效；不能把向量中的旧房源字段当业务真值，最终推荐仍要回查 MySQL。
